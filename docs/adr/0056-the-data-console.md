# ADR-0056 — The data console: one static entry point built by the pipeline

- **Status:** Accepted, by the operator in conversation on 2026-11-20,
  from the plan this record writes down. Nothing it decides is built yet.
- **Date:** 2026-11-20
- **Decided by:** the operator, in conversation on 2026-11-19 and 2026-11-20:
  one place to see and reach the whole data stack, built before any machine
  learning work, reusable by every source, with no second gold layer.
- **Amends:** [ADR-0044](0044-per-job-credentials-and-the-dashboards-publishing-path.md),
  the dashboards' publication: the step that removes stale pages deletes only
  under its own prefix (decision 3 below).

## Context and problem

Lagom's parts are reachable one by one: the reports at `lagom.ofantini.com`,
Dagster at `ops.ofantini.com/dagster`, the models and their tests in the
repository. No page shows how they fit together, what each table means,
where it comes from, or whether the last run left it fresh and tested. dbt
already describes most of this (lineage, descriptions, tests, contracts), but
its documentation site is not published.

The operator wants that page to be the base for later work: each new source,
and later each machine-learning project, should appear in it without changes
to the page's code. The page also supports the project's claim that agents
can build the stack while people can audit it.

## Requirements and constraints

- Nothing resident: the [platform principles](../platform.md#principles) and
  898 MiB of room under the CI ceiling. Work runs as a job in the existing
  run slot.
- Source-agnostic: the console reads metadata, never a source's name.
- Gold stays the only source of truth for data. Nothing the console publishes
  carries a business rule.
- Fail loudly: a stale or failing pipeline is shown as such, never hidden by
  the last good page without its age.
- Public pages carry public data and public metadata only. Operator tools
  stay behind Cloudflare Access ([ADR-0030](0030-operator-uis-behind-cloudflare-access.md)).
- The site at `ofantini.com` never reads Lagom's data
  ([ADR-0039](0039-the-site-in-its-own-repository.md), decision 4).

## Alternatives considered

- **A data catalog or developer portal (DataHub, OpenMetadata, Amundsen,
  Backstage).** Purpose-built for this. Each is a resident server, and
  DataHub and OpenMetadata also need a search engine, so their footprint is
  several gigabytes (estimated, not measured). Rejected: they do not fit the
  node, and their scope exceeds one operator's stack.
- **A link dashboard (Homepage, Homarr).** Small, but resident and static in
  content: it links to tools without describing data or freshness.
  Rejected.
- **A page in the site's repository.** Rejected by ADR-0039, decision 4.
- **A static console generated by the pipeline.** Each `dashboards` run
  already holds the dbt manifest, a read-only view of the lake and the
  Dagster instance. A job can turn them into static pages in the existing
  public bucket. Chosen.

## Decision

1. **The console is static and built by the pipeline.** One more step of the
   `dashboards` job, in the same run Pod with the same read-only credentials,
   writes the console to the environment's dashboards bucket. No new
   resident process, credential or Kubernetes object is added. The image
   carries only the manifest (`dbt parse` opens no connection), so the step
   generates dbt's catalog itself, through the dashboards' read-only profile
   (`data/dashboards/profiles.yml`), never the warehouse's read-write `lake`
   target. The step's memory, catalog generation included, is measured in
   staging and recorded in [Data](../data.md#memory-of-a-run) before
   promotion.
2. **The console is generated from metadata, never from a source's name.**
   Its inputs are the dbt manifest and catalog, the reports declared as dbt
   *exposures*, and the Dagster instance's records of runs and asset checks.
   A **metadata contract** makes every source appear correctly: each gold
   model has a description, an enforced contract and an owner in `meta`,
   and each report is an exposure. A CI check fails when the contract is not
   met. CI also builds the console from a manifest with a synthetic second
   source, which proves the code names no source.
3. **Each producer owns a prefix in the bucket.** The reports, the dbt
   documentation and the console index are written under separate prefixes.
   A producer only deletes stale objects under its own prefix. Today the
   dashboards step deletes every `.html` key it did not just write
   (`publish` in `lagom_orchestration/dashboards.py`), which would delete the
   console.
4. **Two audiences, two places.** The public console shows the architecture,
   the catalog, lineage and documentation, the reports and a summary of
   health: last successful run, data freshness and test counts. It never
   shows error text, logs or configuration. Investigation stays in Dagster
   behind Access, which the console links to. The first version adds no
   route to `ops.ofantini.com`.
5. **Reuse before building.** Lineage and model documentation are dbt's own
   documentation site, as a static file. The console's code is limited to
   the index, the catalog summary and the health summary, which link into
   it.
6. **Health is read when the console is built.** The step reads run and
   asset-check results from the Dagster instance it runs in, and freshness
   from the lake. Each page states when it was built, as the reports do. A
   failed `usgs` run does not trigger the `dashboards` job, so a stale
   console shows its age rather than claiming fresh data.

### Later stages, decided in their own records

- **Queries in the visitor's browser** (DuckDB-WASM over gold). The operator
  rejected in-browser filtering of the reports
  ([ADR-0043](0043-the-dashboards-filter-in-the-browser.md)), and ad-hoc BI
  has its own entry trigger ([ADR-0055](0055-superset-spike.md)). This stage
  needs its own record that answers both. Its constraints are set now. If it
  needs a copy of gold, the copy is a publication, not a layer: rebuilt by
  every successful run after the tests, reconciled with gold by row counts,
  written to a new location per run and made visible by a final pointer
  swap. A spike first tests whether the browser can read the DuckLake
  directly, which would make the copy unnecessary.
- **Requests to an AI from the console.** A request becomes a GitHub issue,
  an agent answers with a pull request, and the usual gates apply. The agent
  never acts on the cluster. This stage changes guardrails and needs its own
  record.

## Consequences

**Positive.** One public address explains the stack and its state. A new
source, and later a model and its predictions, appears when it meets the
metadata contract. The contract also improves the dbt project itself:
descriptions, owners and exposures become required. Documentation that the
pipeline generates cannot drift from the code.

**Negative.**

- The `dashboards` job grows. A failure in the console step fails the job.
  The reports are uploaded first, so a console failure leaves them current
  and the console stale with its age shown.
- The metadata contract is a new gate on every gold model.
- dbt's published documentation exposes compiled SQL and file paths. The
  repository is public, so the SQL is not new, but the first publication is
  reviewed for hostnames, credentials and environment values before it ships.

## Risks, cost, and reversal

- **Unverified:** whether R2's custom domain serves an index document at `/`.
  If not, the console lives at a named path and a redirect at the zone sends
  `/` to it. This is checked in the stage that publishes the index.
- **Unverified:** whether dbt's static documentation loads anything from
  another host. The CI check that rejects external loads on the reports is
  applied to it.
- **Cost:** CI minutes and a longer `dashboards` run. No resident memory and
  no new secret.
- **Reversal:** remove the console step and its prefixes. The reports and the
  pipeline do not depend on it.
